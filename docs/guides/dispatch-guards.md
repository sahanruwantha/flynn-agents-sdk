# Dispatch guards and lifecycle notifications

Pass `guards=(DispatchGuard("scope", check), ...)` to Runtime or Session. Each async
check receives the exact operation identity, prepared inference request and validated
ToolCall, and returns `GuardDecision(allowed, reason)`. Guards run serially after inference
and argument validation, before tool or external-action reservations. They may inspect
application authority, but must not perform the external action they are authorizing.
The harness still owns file safety, confinement, authority fences and domain policy.

SQLite schema 5 records required guard identities atomically with operation admission.
Each decision is append-only and foreign-key-bound to its requirement. The dispatch
transaction refuses any missing or denied decision before spending tool/action capacity.
Guards cannot alter arguments or widen grants. A denial raises DispatchDenied; invalid
returns, exceptions and cancellation fail closed. No fallback, retry or automatic recovery
runs. Inference already spent remains accounted. Reconciliation is explicit and never
re-executes an uncertain tool. Unguarded operations declare an empty requirement set.

Pass a synchronous `on_event(Event)` callback for immediate lifecycle notifications.
Runtime persists each event before notifying: started, inference_returned, guard_allowed /
guard_denied, tool_dispatched, tool_returned, observed / committed, and failure diagnostics.
Callbacks must not block or mutate application authority. They are not authorization hooks.
A callback failure stops execution; its failure event is recorded without invoking the
failing callback again. Already-returned evidence and completed evaluations remain durable.
A notification failure after a dispatch intent conservatively leaves that intent unresolved
if the tool has not returned. The SDK never retries it.

The tables `guard_requirements`, `guard_decisions` and `lifecycle_events` are immutable
history. Event rows are notifications of recorded boundaries, not a second control state:
a process death can occur between the control transaction and event publication. Inspect
operations, reservations and evaluations to resolve progress; missing events do not undo
committed work. In-process Runtime.events is a presentation snapshot, not an audit authority.

Only schema 5 executes. Schemas 2–4 remain read-only audit evidence; their absent guard/event
tables are exposed as empty, without inventing authorization or migrating old databases.
A schema-4 SQL fixture generated by the preceding SDK pins historical inspection behavior.
